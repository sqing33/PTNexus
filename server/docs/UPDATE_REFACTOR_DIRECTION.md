# PT Nexus 在线更新改造方向（阶段性）

## 1. 背景与目标

当前更新模型主要基于“拉取源码 + 覆盖文件 + 重启进程”。  
在 Go 化和多运行形态（容器 + 桌面）并行后，这种方式的主要问题是：

- 更新载体是源码，不是可运行产物，现场不确定性高。
- 覆盖式更新容易出现“部分更新成功、部分失败”的中间态。
- 回滚依赖备份完整性，恢复成本高。
- “热更新”语义不清晰，实际仍是停服切换。

本阶段改造目标：

- 从“源码更新”切换为“产物更新”。
- 统一更新流程为可校验、可回滚、可观测的标准状态机。
- 同时支持容器与桌面两条链路。
- 先实现“秒级抖动可接受”的无感升级体验，不追求进程内代码热替换。

## 2. 核心原则

1. 更新对象必须是构建产物（artifact），不是仓库源码。
2. 更新动作必须先校验再切换，不允许直接覆盖运行目录。
3. 切换动作必须原子化（一次指针/目录切换），避免半升级状态。
4. 新版本必须经过健康检查，不通过则自动回滚。
5. 数据目录与程序目录分离，避免版本切换影响运行时数据。

## 3. 目标架构（高层）

### 3.1 统一更新清单

引入统一的更新元数据（建议名：`UPDATE_MANIFEST.json`），描述：

- 版本号、发布时间、更新策略（普通/强制/禁更）
- 不同运行形态下的下载地址（容器镜像、桌面运行时包）
- 文件哈希（sha256）与大小
- 兼容约束（如最小 updater 版本、迁移策略提示）

### 3.2 统一更新状态机

更新流程统一为以下阶段：

1. `check`：检查远端版本与本地版本
2. `pull`：下载更新包/拉取镜像
3. `verify`：校验 hash 与包完整性
4. `install`：执行原子切换
5. `health`：健康检查
6. `rollback`：失败自动回退

## 4. 两条链路的方向

## 4.1 容器链路（Docker Compose / 单机）

方向：镜像更新优先，不在业务容器内做源码更新。

- 主路径：`pull 新镜像 -> 重建容器 -> 健康检查 -> 失败回退旧镜像`
- 触发方式：
  - 推荐：宿主机侧更新代理（Host Agent）执行更新动作
  - 兜底：UI 给出可执行命令，由运维在宿主机手动执行
- 约束：避免把 Docker 控制权限直接暴露到业务进程

## 4.2 桌面链路（sidecar/runtime）

方向：运行时版本化目录 + 原子切换。

- 目录模型建议：
  - `releases/<version>/`：完整运行时
  - `current`：当前生效版本指针
  - `staging`：下载与解压临时区
- 更新过程：
  - 下载到 `staging`
  - 校验通过后切换 `current`
  - 启动并做健康检查
  - 失败回切旧版本

关于 updater 自更新：

- 可以支持，但应采用“两阶段替换”思路，避免覆盖正在运行的可执行文件。
- 该能力建议放在第二阶段完成，先保证主链路稳定。

## 5. “热更新”边界定义

本项目建议采用“工程化热更新”定义：

- 不做进程内代码热替换（风险高、收益低）。
- 使用“优雅停机 + 快速重启 + 原子切换”达到接近热更新体验。
- 用户体验目标是秒级抖动，而不是严格零中断。

## 6. 迁移策略（阶段性）

### Phase 1：模型切换（最小可用）

- 建立更新清单与产物发布流程
- updater 改为读取清单、下载产物、校验产物
- 保留现有更新入口交互（check/pull/install）

### Phase 2：稳定性增强

- 引入更新任务状态与进度可观测能力
- 引入健康检查门禁与自动回滚
- 完成桌面版本化目录切换

### Phase 3：双链路统一体验

- 容器侧接入 Host Agent（或形成标准手工流程）
- 桌面侧补齐 updater 自更新
- 统一错误码、提示文案、日志语义

### Phase 4：旧链路收敛

- 下线源码拉取更新主路径
- 将旧 mappings 覆盖逻辑降级为应急路径或移除

## 7. 验收口径（方向级）

- 更新失败时，服务可自动恢复到上一个可用版本。
- 任意失败点（下载失败/校验失败/启动失败）不会破坏当前稳定版本。
- 更新链路可以清晰回答“当前在哪个阶段、为什么失败、是否已回滚”。
- 容器与桌面两条链路在产品层的交互语义保持一致。

## 8. 当前阶段结论

在项目结构尚未最终定型前，优先锁定“更新模型”而非“代码位置”：

- 先统一协议与状态机
- 再按最终目录结构落实现
- 最后逐步替换旧链路

这样后续即使目录继续重构，也不会推翻更新体系本身。

## 9. 与当前 Go 二进制版本的适配（落地说明）

当前仓库对于 **Go 二进制发布**采用 `artifact` 主链路：

- 通过 `UPDATE_MANIFEST.json` 提供更新产物（压缩包）URL + mirror_urls + sha256
- updater 使用 `/update/pull` 下载并校验产物，解压到 staging
- `/update/install` 执行版本目录切换（`releases/current`）+ 健康检查，失败自动回滚
- 容器可执行在线产物更新，不再依赖 git 拉源码

元数据发布约定：

- `CHANGELOG.json` 是唯一人工维护源（版本说明 + `artifact_sources`）。
- `scripts/build-update-artifacts.sh` 从 `CHANGELOG.json` 自动生成 `UPDATE_MANIFEST.json`。
- updater 默认并行探测 GitHub/Gitee 的元数据地址，自动选择可用源。

对应 manifest 与产物内容约定见：`server/docs/UPDATE_MANIFEST_SPEC.md`。
